# AI 电商工作台 UI 与可靠性重构设计

日期：2026-09-04  
状态：已确认方向 A，待书面规格复核  
范围：`#ai-commerce` 工作台、历史记录抽屉、上传/生成状态、工作台内音乐入口；不改首页主视觉、不改结果数据结构、不新增计费能力。

## 1. 背景与目标

现有 AI 电商工作台已经具备登录、产品资料录入、图片上传、方案生成、历史记录和额度管理能力，但界面与状态组织没有形成单一主线：表单、摘要、历史三列同时争夺注意力；失败、可提交和上传进度可以同时出现；历史区内容很少时仍占据大块画布；移动端悬浮音乐入口还可能覆盖主操作。

本次不是换肤，而是重构工作台的视觉层级和交互状态。完成后应让用户在任何时刻都能回答三件事：我现在在哪一步、系统正在做什么、下一步只能做什么。

成功标准：

- 首屏只突出当前任务和一个主操作，不出现相互矛盾的按钮或提示。
- 桌面端在 1440px 宽度下具有稳定版心、明确主次和自然留白；1024px 不拥挤；390px 无横向滚动和遮挡。
- 图片上传、会话刷新、项目清理、重试和历史刷新形成可验证的状态闭环。
- 视觉保持暗色、高级、克制、有技术感，并与站点现有浮动导航和首页气质连续。
- 深色与浅色模式均可读，不依赖荧光色表达状态。

## 2. 设计依据

### 2.1 参考站中保留的逻辑

参考 `https://tblog.mmzhiku.xyz/` 的以下原则，而非复制其内容和主题：

- 导航悬浮在内容上方，默认安静，当前项和展开菜单才提高对比度。
- 一级导航数量有限，二级入口按需展开，不把全部功能铺在首屏。
- 大画面负责氛围，小型面板负责操作；两者不会同时使用强边框和强背景。
- 动效集中于进入、展开和当前状态，不让所有组件持续闪动。

### 2.2 外部 UI 原则

采用 Linear 2026 UI refresh 的两条原则：辅助界面不应争夺尚未获得的注意力；结构应被感知而不是被大量边框直接画出来。落实为：弱化导航和历史，减少无意义分割线，只让当前任务、错误和主操作拥有高对比度。

### 2.3 明确不采用的方向

- 不做传统后台式永久三栏布局。
- 不用满屏网格、荧光描边、巨型等宽英文标签堆叠“科技感”。
- 不用多个绿色按钮、红框和进度条同时表达同一状态。
- 不照搬参考站的动漫背景、内容文案或完整组件外观。

## 3. 信息架构

页面拆成四层：

1. **站点层**：沿用全站浮动导航，但工作台页面降低导航不透明度和阴影。
2. **工作台标题层**：一行显示页面名、剩余额度、历史入口和账户状态；不再使用占据大面积的介绍 Hero。
3. **任务层**：顶部步骤轨道 + 当前步骤编辑区 + 紧凑上下文摘要。
4. **辅助层**：历史抽屉、重新登录提示、删除确认和音乐弹层，默认均不占主画布。

桌面端工作区使用 `max-width: 1280px`，左右安全边距为 `clamp(24px, 4vw, 64px)`。内容区是两列而不是三列：

- 主编辑区：约 820–880px，可伸缩。
- 上下文摘要：约 280–320px，只展示当前平台、模式、图片和输出范围。
- 历史记录不再是第三列，改为从右侧进入的 420px 抽屉。

1024px 以下改成单列，摘要成为步骤内容下方的横向摘要条。640px 以下每次只显示一个步骤，主操作固定在底部安全区上方。

## 4. 核心流程

### 4.1 步骤

固定为三个用户可理解的步骤：

1. **产品**：产品名、图片、类目与核心卖点。
2. **市场**：平台、受众、品牌语气、竞品和限制条件；快速模式只保留平台与可选补充。
3. **确认**：素材授权、输出预览、剩余额度和提交。

桌面端允许返回已完成步骤；正在上传或生成时锁定会影响当前任务的字段。移动端使用顶部紧凑步骤条，不用长表单一次铺完。

### 4.2 单一主操作

主操作区由页面状态机驱动，每个状态只显示一个主要动作：

| 状态 | 主动作 | 辅助信息 |
| --- | --- | --- |
| 输入未完成 | `继续` 或禁用的 `生成方案` | 只列出缺少的项目 |
| 可提交 | `生成视觉方案` | 本次消耗与输出范围 |
| 创建/上传/排队/生成 | 不可重复点击的进度动作 | 当前阶段和可取消性 |
| 可恢复失败 | `重试本次生成` | 精确原因和不会重复扣费说明 |
| 身份需恢复 | `重新连接账号` | 文本草稿保留说明；若需 OAuth 跳转则提示重新选择本地图片 |
| 不可恢复失败 | `新建一次分析` | 清理结果与支持信息 |
| 完成 | `查看方案` | 保存时间和历史入口 |

错误态必须替换正常提交按钮，不能在错误卡下方继续显示绿色生成按钮。“资料与授权已齐”仅在 `idle + validation.ok` 时出现。

## 5. 页面组件

### 5.1 `CommerceStudioHeader`

- 左侧：`AI 电商视觉工作台` 与一句短说明。
- 右侧：`剩余 3 次`、历史按钮、账户头像/名称。
- 历史按钮显示项目数量，点击打开抽屉。
- 页面标题桌面为 36–44px，手机为 28–32px，不使用当前面板内 34px 以上的大标题。

### 5.2 `CommerceStepRail`

- 三个步骤横向排列，使用数字、名称和极细连接线。
- 当前步骤使用文字高对比与 2px 状态点；已完成步骤使用小勾；未开始步骤降噪。
- 不使用大色块标签页。

### 5.3 `CommerceBriefEditor`

- 每一步只有一个清晰标题和必要字段。
- 输入控件使用同一高度、圆角和边界；标签位于控件上方，不再把编号、英文标签、中文标题分散成多列。
- 上传区在空态是低对比虚线面，选图后变为 3:2 缩略图网格；每张图显示文件名、大小和移除按钮。
- 快速/专业模式使用紧凑分段控制，并在切换时保留已填内容。

### 5.4 `CommerceRunPanel`

- 桌面端是右侧紧凑摘要，不承担长篇解释。
- 输出说明压缩为 `3 套主图方向 · 8–12 屏详情分镜 · 中俄提示词`。
- 状态、进度、错误和 CTA 共用一个固定区域，通过状态替换内容，避免页面高度跳变和重复信息。
- CTA 最大宽度约 220px，不再使用占满整个侧栏的荧光绿巨型按钮。

### 5.5 `CommerceHistoryDrawer`

- 右侧覆盖式抽屉，桌面宽 420px，移动端为全屏底层页面。
- 顶部有搜索/筛选入口但首版只实现状态筛选：全部、完成、处理中、未完成。
- 项目卡仅显示名称、平台、状态、更新时间、图片保留状态和操作菜单。
- 没有 generation 的项目显示“未完成草稿”，不能显示成正常项目。
- 上传失败且后端删除成功后，立即从本地列表移除并后台重新拉取；不会保留截图中的幽灵项目。

### 5.6 `CommerceStatusSurface`

统一承载加载、成功、失败和身份恢复。错误由代码映射到可操作类型：

- `AUTH_REQUIRED`：身份无效，先尝试静默刷新；失败后显示重新登录。
- `ORIGIN_FORBIDDEN`：部署来源配置错误，提示站点维护而不是要求用户登录。
- `VALIDATION` / `UPLOAD_INVALID`：指出具体图片或字段问题。
- `NETWORK`：保留草稿并允许原地重试。
- `RATE_LIMITED` / `CREDITS_EXHAUSTED`：显示等待或额度动作。
- `SERVICE_ERROR`：说明项目与扣费处理状态，避免技术堆栈。

### 5.7 工作台音乐入口

- 保留右下角小型音乐启动器，但工作台内默认缩为 42–46px。
- 关闭状态只有按钮本身可接收点击；外层容器和隐藏弹层使用 `pointer-events: none`，启动器使用 `pointer-events: auto`。
- 移动端启动器位于底部 CTA 上方，二者至少间隔 12px。

## 6. 视觉系统

### 6.1 色彩

深色模式：

- 页面背景：近黑中性灰，不带大面积紫色或绿色偏色。
- 主表面：比背景提高一个明度层级。
- 浮层：再提高一个层级并使用轻微模糊。
- 边界：白色 7–10% 透明度，只用于真实分组。
- 主文字：柔和白；次文字：约 62% 对比；说明文字：约 42%。
- 品牌绿：只用于当前步骤、可执行 CTA、成功状态和小范围光点，占屏面积不超过约 5%。
- 错误色：低饱和珊瑚红，配合图标和文案，不只靠颜色。

浅色模式使用暖灰白背景、纯白表面和深灰文字，保持相同层级关系，而不是简单反转颜色。

### 6.2 字体与节奏

- 中文正文使用现有系统无衬线字体栈；数字、编号和短状态使用等宽字体。
- 页面标题 36–44px；步骤标题 22–26px；正文 13–15px；标签 11–12px；元信息不低于 10px。
- 基础间距单位 4px，常用节奏为 8/12/16/24/32/48。
- 卡片圆角控制在 14–18px；输入框 10–12px；胶囊只用于筛选和模式切换。
- 阴影只用于导航、抽屉和弹层，不给普通表单卡片叠加厚重投影。

### 6.3 动效

- 页面切步：180–220ms 的透明度与 8px 位移。
- 抽屉：220–260ms，配合背景遮罩。
- 上传/生成：单个状态点或细进度线，不使用多个同时闪动的动画。
- 遵守 `prefers-reduced-motion`，关闭位移、循环脉冲和非必要粒子动画。

## 7. 状态与数据流重构

### 7.1 显式状态机

工作台使用一个可判定的阶段，而不是由 `status + error + progress + validation` 各自决定显示：

`editing → validating-session → creating-project → uploading → starting-generation → generating → completed`

失败分支为：

`recoverable-error | auth-recovery | terminal-error`

视图从这一阶段派生：主按钮、错误表面、字段禁用、历史刷新和进度文案只能由同一阶段决定。

### 7.2 会话保护

每次产生写操作前调用统一的 `getFreshAuthenticatedSession()`：

1. 读取当前 session；缺失则进入身份恢复。
2. token 已接近过期或上次函数返回 401 时，只进行一次 `refreshSession()`。
3. 使用远端 `getUser()` 确认不是匿名用户。
4. 调用 Edge Function 时显式传入该 session 的 `Authorization: Bearer <access_token>`；publishable key 仍由 Supabase SDK 放入 `apikey`。
5. 401 只允许刷新并重放一次，防止无限循环或重复生成。

这解决当前“数据库 RPC 可以创建和删除项目，但 Edge Function 上传阶段报告登录失效”的断层。任何 token 均不得写入日志、DOM、测试快照或错误信息。

### 7.3 上传与清理事务

- 保持 `createProject → reserve/upload/finalize → startGeneration` 顺序。
- 项目创建后先在本地标记为 `draft-uploading`，不立即作为正常历史项目展示。
- 上传失败后执行项目清理；清理成功立即刷新历史并清除临时卡片。
- 清理失败显示“需要刷新恢复”的终止态，禁止重复上传以避免重复对象。
- 重试沿用同一次尝试的本地 `File` 和输入；只有内容发生变化才创建新 attempt。
- OAuth 完整跳转无法安全保留浏览器 `File` 对象：静默刷新成功时图片保留；若必须重新登录，文本草稿可短期写入 `sessionStorage`，回站后明确要求重新选择图片。不得把图片 base64 写入浏览器存储。

### 7.4 错误映射

先按后端结构化 `code` 判断，再看 HTTP 状态和网络错误。不能继续用“所有 403 都是登录失效”的规则。`ORIGIN_FORBIDDEN`、RLS 权限拒绝、管理员权限拒绝和真正的 session 失效必须分别显示和记录。

## 8. 文件边界

为避免现有单文件继续膨胀，实施时按以下职责拆分：

- `CommerceStudioPage.tsx`：页面组合、用户作用域和路由入口。
- `useCommerceRun.ts`：提交状态机、会话恢复、重试和轮询。
- `CommerceProjectForm.tsx`：字段状态、校验和步骤推进。
- `CommerceRunPanel.tsx`：摘要、状态面和唯一主操作。
- `CommerceHistoryDrawer.tsx`：历史加载、筛选和项目操作。
- `commerceErrors.ts`：结构化错误分类与用户文案。
- `commerceRepository.ts`：数据库、Storage 和 Function 调用，不承载页面状态。
- `commerce.css`：保留入口文件，拆分为 tokens/layout/form/status/history/result/admin 等模块；结果页和后台只做必要兼容，不在本次视觉重构范围内全面重写。

组件之间传递领域状态和事件，不传 Supabase client 或原始后端 error。

## 9. 无障碍与响应式

- 步骤轨道使用可理解的 `aria-current="step"`。
- 状态变化使用单一 `aria-live` 区域，避免多处同时播报。
- 抽屉打开后焦点进入标题，Escape 关闭，关闭后焦点回到历史按钮。
- 所有交互区域最小 44×44px；键盘焦点清晰可见。
- 颜色对比达到 WCAG AA；错误、完成和处理中均有文字/图标辅助。
- 390px 宽度下 `document.documentElement.scrollWidth === window.innerWidth`。
- 虚拟键盘打开时底部 CTA 不遮挡当前输入框。

## 10. 测试与验收

### 10.1 单元与组件测试

- 失败状态不会同时渲染“重试”和“生成视觉方案”。
- `资料与授权已齐` 只在可提交的编辑态出现。
- 401 触发一次 session refresh 和一次请求重放；第二次失败进入登录恢复。
- Edge Function 请求显式携带当前用户 session token，测试只断言 header 存在和来源，不输出值。
- `ORIGIN_FORBIDDEN` 不会映射为“登录已失效”。
- 上传失败清理成功后刷新历史并移除临时项目。
- 隐藏的音乐弹层不会命中工作台或管理后台按钮。
- 切换快速/专业模式不会丢失输入。

### 10.2 Playwright 视觉与交互验收

- 1440×1000：检查版心、两列比例、首屏 CTA、历史抽屉、错误替换态和导航层级。
- 1024×900：检查单列切换、摘要位置和历史抽屉宽度。
- 390×844：检查步骤切换、上传预览、键盘、底部 CTA、音乐按钮和横向溢出。
- 深/浅模式各截图一组；减少动态模式截图一组。
- 控制台无应用 error；网络检查中不保存或展示认证 header。

### 10.3 生产冒烟

使用站长账号和一张小型合法测试图片执行：登录 → 建项目 → 上传 → 启动 DeepSeek → 等待结果 → 打开历史。验证：

- 上传 Function 返回成功，不出现虚假“登录失效”。
- 只消费一次额度；模型失败时按现有规则退款。
- 历史不存在已被清理的幽灵项目。
- 页面底部所有管理和表单按钮均可点击。

## 11. 实施顺序与风险控制

1. 先建立错误分类、会话保护和上传状态机测试，修复真实故障。
2. 再拆分 Run Panel 和历史抽屉，消除三栏和冲突状态。
3. 最后应用视觉 token、响应式布局与音乐点击区域修复。
4. 本地测试和构建通过后启动预览，用 Playwright 做三档宽度验收。
5. 生产发布后执行一次真实小图冒烟；失败则不继续扩大变更，按部署提交回退。

主要风险是 OAuth 完整重登无法保留本地文件。设计明确采用“优先静默刷新；必须跳转时保留文字、要求重新选择图片”，不以不安全的浏览器持久化规避平台限制。

## 12. 非目标

- 不在本次新增真正的图片生成模型或修改 DeepSeek 输出协议。
- 不重做首页、音乐可视化页、留言页和管理后台整体视觉。
- 不新增付费、套餐、微信登录或团队协作。
- 不改变 7 天图片清理、额度扣除和管理员 999/无限额度规则。

## 13. 规格自检

- 无 TBD、TODO 或未决设计项。
- 页面结构、组件职责、状态机和测试场景一致。
- 明确区分静默 session 刷新与必须 OAuth 重登时的文件限制。
- 范围聚焦于工作台 UI、上传可靠性、历史一致性和音乐遮挡，不扩大到其他页面。
